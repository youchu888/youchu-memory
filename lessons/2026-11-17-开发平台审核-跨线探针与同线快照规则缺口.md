# 开发平台审核：同线快照 / 中间步探针（S3 规则缺口）

## 背景

工作狂人群消息（2026-11-17，@anna_cute9）：提审被拒。先报「只认同线快照在前、不认跨线探针」；随后根因定位到发布审核 **S3 闸** 的依赖覆盖检查。属审核规则漏洞，非开发写法问题；拟修待知秋确认后上线。

## 坑 / 错误做法

- 把 S3 依赖覆盖拒审当成步骤 SQL/挂法写错，从 S1 重来或为此重跑数据。
- 以为调度器不支持中间步探针（运行时其实已支持；拦的是审核闸）。

## 正确做法

- **S3 依赖覆盖（现状缺口）**：只扫同线前序步产出 + **该线第一步**探针，**不认**中间步自己配的探针 → 中间步挂探针会被误拦。
- **拟修方向**（待知秋确认）：审核同时认 **本步** 与 **同线前序步** 所配探针。
- 规则修好上线后：在**原** dev-session 重新提交即可；不必从 S1 重来，不必重跑数据；等群里 @ 再提，勿提前重提。
- 同槽跨线先后以步骤级 runlog/探针声明为准（见 pipeline-runner `Probe.scala`），不能单靠同线快照排序。

## 验证

- 中间步自配探针的会话，S3 依赖覆盖不再误拒。
- 原 session 重提可通过，且无需重跑数据。

## 关联

- `pipeline-runner/src/main/scala/com/dc/pipeline/Probe.scala`（runlog 探针、同槽跨线）
- `docs/design_runner_concurrency_and_platform_integration_20261002.md`

## 变更记录

- 2026-11-17：初记——规则漏认跨线探针；修好后原 session 重提；勿 S1 重来/勿重跑。
- 2026-11-17：根因细化——S3「依赖覆盖」只认同线前序产出 + 首步探针，不认中间步自配探针；拟修认本步及同线前序步探针；待知秋确认改代码。
- 2026-11-17：**更正撤回拟修**——「线中间不能配探针」为既定审核规则，不放宽；中间步被拒按 design 换线或改 `line`/`after_step`，勿等认中间步探针的代码修复。

## 更正（同日后续群消息 · 优先读本节）

工作狂人撤回「S3 漏规则、拟让审核认中间步探针」结论：**同线中间步不得自配探针**是产品既定规则，与 runner 运行时能否挂探针无关，审核闸 intentionally 只认该线首步及同线前序步产出/首步探针。

**开发侧正确动作**：

1. 发布被拦时把**完整报错**（截图或原文）发到协作群。
2. 同步说明 `design.md` 里 ` ```spark-scheduling ` 块的 **`line`**（所属调度线名）与 **`after_step`**（挂在本线哪个前序步之后；新建线常为空串）。
3. 由审核人按报错逐表判断：**换线**还是**改调度声明**（可先用 `runner__get_scheduling_context` 重判线归属，再改块后重提）；不必从 S1 重来，不必为重审重跑数据。
4. **勿**依赖「平台将放宽中间步探针」——该修法已撤回。

上文「规则漏洞 / 拟修 / 待知秋改代码」仅作当日误判记录，**不再适用**。
