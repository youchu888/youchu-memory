# 开发平台审核：S3 外部探针仅组入口（线中间禁配）

## 定稿规则（优先）

知秋定、审核闸**故意卡**、**不放宽**（非平台漏改）：

1. **外部探针只能配在组入口那一步**；同线**中间步骤不能配**探针。
2. 中间步要过 S3：二选一——**改成某条线的入口步**，或**去掉中间步上的探针**，依赖改由同线前序步保证。
3. 被拦时交：**S3 原报错**（截图/全文）+ `design.md` 里 `spark-scheduling` 的 **`mode` / `line` / `after_step`**；改完后**重跑 S3**（不必从 S1 重来、不必为此重跑数据）。
4. 例：`dws_user_promotion_behavior_h_h` 若在中间步自挂探针会被卡，按上两条改发布声明。

## 背景（同日误判 → 撤回）

群内曾先后称「规则漏认中间步/跨线探针、拟修认本步+前序探针」；随后更正撤回。runner 运行时或可挂中间步探针，**审核闸 intentionally 不认**，与「漏规则」无关。

## 坑 / 错误做法

- 等「平台放宽中间步探针」或改审核代码后再提。
- 把 S3 依赖覆盖拒审当成 SQL 写错，从 S1 重来或为此重跑数据。
- 拒审只改 SQL、不交报错与 `mode`/`line`/`after_step`，审核人无法判断换线还是改声明。

## 正确做法

- 写 `spark-scheduling` 时：探针只挂在**该组/该线入口步**；中间步依赖靠同线前序产出。
- 中间步被 S3 拦：入口化（换线或改 `after_step` 使本步成入口）**或**删本步探针声明后重提 S3。
- 可先用 `runner__get_scheduling_context` 重判线归属，再改块。

## 验证

- 入口步带外部探针可通过 S3 依赖覆盖；中间步自配探针应被拒。
- 改声明后原 session 重跑 S3 即可，无需重跑业务数据。
