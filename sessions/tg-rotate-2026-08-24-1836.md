## 现在主流是什么

2025–2026 对外叫得最多、落地最多的是 **Semantic Layer（语义层）**，不是纯 Ontology，也不是老式「一张指标登记表」。

典型代表：dbt MetricFlow、Cube、LookML、Snowflake / Databricks 的 semantic / metric views；Open Semantic Interchange（OSI）也在推可交换语义定义。

但业界说「语义层」时，经常把两层叠在一起：
- **Metric Store**：管 KPI 怎么算（聚合、时间窗、版本、主实现）
- **Semantic Layer 本体部分**：管 entity、维度、join、谁能怎么切

纯 **Ontology / Context Layer** 是上升趋势（给 AI 推理用），但还不是多数数仓团队的默认交付形态——贵、慢、技能栈不同。

一句话：**主流品牌是语义层；可执行内核多数是「指标层 + 一点实体/维度语义」。**

## 哪个符合你们需求

对照你们已经钉死的约束（不做 Headless BI、AI 只 propose、要挂已有 DWS/ADS 列、同名拆条、禁比率进 canonical、published 要 req_ref、先治理 264 条脏库），最贴的是：

**以 Metric Store 为核的轻量 Semantic Layer**  
（≈ dbt MetricFlow 路线，不是 Cube 全栈，也不是全量 Ontology）

| 方案 | 适不适合 | 原因 |
|------|----------|------|
| 纯维度/指标集市 | 不够 | 你们痛点是口径治理与多实现，不是再建一套星型 |
| 纯 Metric Registry（现稿偏这个） | 偏轻 | 只登记名字/公式，缺 entity·维度·适用范围 |
| **Metric-centric Semantic Layer** | **推荐** | 正好覆盖「实际指标 + 多名字 + 多实现 + 时间/聚合语义 + 绑定物理列」 |
| 全量 Ontology | 过重 | 建设成本高，和当前「止血 + 迁 264」节奏不匹配 |
| 完整 Context Layer | 中期加，不首刀 | 血缘/owner/发布门禁你们已有半套，可挂接，不必一次做成 |
