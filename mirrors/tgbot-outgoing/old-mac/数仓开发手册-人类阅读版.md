# 数据中心数仓开发手册（人类阅读版）

> 版本：2026-07-30 · 维护：又初  
> 适用范围：test 开发 → test 验数 → 提审 → prod 上线全链路

---

## 一、这套流程解决什么问题

数仓改动（建表、改 SQL、改口径）不能「本地改完就算完」。标准路径是：

**需求对齐 → 开发平台建 session → 写 spec/design/SQL → test 海豚跑通 → 对账验数 → git 提交 → 提审 → admin 发 prod → 次日盯产出**

好处：每一步有凭证（PI、行数、commit SHA、publish-run），出问题能回溯，prod 不会被人手改 SQL 悄悄上线。

## 二、环境与分工（先搞清楚连哪、谁能动哪）

| 环境 | 典型用途 | 海豚 | StarRocks |
|------|----------|------|-----------|
| **test** | 开发、单分区补跑、验数 | DS 3.1.9 @ 43.212.183.54 | test SR（数据常稀疏，勿当 prod 结论） |
| **prod** | 对账、datacheck、看现网 | DS 3.4.1 @ 13.212.153.182（改 task 须审核） | prod SR @ 52.221.240.167:9030 |

**分工习惯**：
- 开发同学：test 写 SQL、平台 publish-test、补数验数、提 request-publish
- 工作狂人：独立复审 SQL/依赖/数字，不代点 prod
- 知秋 / admin：prod 发版口令、终审放行
- **禁止**：开发侧自发 prod、手搓海豚 REST 改正式 task（无审计）

## 三、仓库与目录（代码放哪）

- 主仓：`dmp/dc-parent`（本地 CHcode），ETL 在 `ops_system/` 按层分目录
- 单任务典型结构：`ops_system/<层>/<任务名>/`
  - `spec.md` — 需求与验收标准
  - `design.md` — 口径与表设计
  - `*_ddl.sql` — 建表/改表
  - `*.sql` — 业务 SQL
  - `task.yaml` — 海豚 project/wf/task、调度、上下游
  - `playbook.md` — 验数剧本（可选）
- 平台 session 的 `project_id` 必须写 **`dmp/dc-parent`**，否则插件需求列表看不见

## 四、开发平台 7 个阶段（一张图看懂）

```
Stage1 需求(spec) → Stage2 设计(design) → Stage3 编码(SQL/DDL)
    → Stage4 test跑通 → Stage5 prod只读核对 → Stage6 git提交
    → Stage7 提审 + prod发布
```

### 4.1 新建需求（第一次做这张表/这个 task）

1. 与业务/知秋对齐：表名、分区、上下游、验收指标
2. 开发平台 **建 dev-session**（API 或 VS Code 插件）
3. 按 stage 1→3 写 spec、design、SQL
4. test 执行 DDL（如有新表）
5. **平台 publish-task-sql 到 test 海豚**（不要手改海豚 UI）
6. test **补数**（COMPLEMENT_DATA 单分区），拿到 **PI SUCCESS + 表有数 + 行数合理** 三件套
7. 按 playbook 对账（默认查 T-1 业务日）
8. stage6：`git add` + `commit` + `push origin/dev`
9. stage7：**request-publish**，等狂人复审 + 知秋/admin 发 prod

### 4.2 改已有 task（第二版、第三版…）

已上线 session 要改 SQL 时：

1. 平台点 **「确定修改 / start-modify」** → `task_version` 自动 +1，stage 从指定步重置
2. 改 SQL/yaml，**test 里该 wf 下所有相关 task 都要重跑**（日批+小时批都不能跳）
3. 再走 stage4→6→7

**铁律**：提审前 `state_json` 里要有真证据（查库结果、prod dry-run、commit SHA），不能只把 stage 标成 done。

## 五、test 验数（怎么算「跑通了」）

最低门槛（每张表 / 每个 task）：

1. 海豚 **Process Instance = SUCCESS**
2. 目标分区 **有行**（`SELECT COUNT(*) WHERE dt=...`）
3. 行数 / 关键字段 **符合预期**（和上游比、和前日比、按 playbook）
4. hourly 任务：至少跑 **2 个时间窗**，最好含跨日边界
5. 主键 upsert 表：至少 **2 个不同 dt** 各补一次，确认幂等

对账默认连 **prod** 做 datacheck（test 数据太稀会误判）。轻量探表才用 test。

## 六、prod 上线（谁能发、怎么发）

1. test 全过 + git 已 push → 开发侧 **request-publish**
2. 狂人 **独立复审**：git diff、live SQL、test 证据、依赖/DAG
3. 知秋拍板后 **admin** 走平台 `publish-from-repo` 或发布向导
4. 每个 task **单独推**，推完立刻验五项：
   - publish-run 成功且 task_version 对齐
   - prod live SQL 含本次改动关键字
   - workflow ONLINE
   - schedule ONLINE（wf 上线后 schedule 不会自动跟，必查）
   - session stage7 = done
5. **次日**看定时任务自然跑的分区是否出数

**DDL + 写表 ETL 必须同批上线**；只改表不改 SQL（或反过来）prod 定时跑会秒挂。

---

## 七、海豚操作红线（改 task 前必读）

1. 改 task 流程：**OFFLINE wf → PUT → ONLINE wf → schedule ONLINE**（缺最后一步等于不上线）
2. 正式改动走 **平台 publish-task-sql**，禁止 REST 整包覆盖 task_params（会清空 localParams）
3. test / prod 的 project_code、wf_code、task_code **不通用**，查 `.claude/dolphin/wf_cross_env_map.yaml`
4. 改 cron：schedule 在 ONLINE 时不能直接 PUT，须 **OFFLINE → 改 → ONLINE**
5. Spark 新链路：launcher 走 `ops_system/_templates/`，先 step0 DDL bootstrap 再跑数

## 八、SQL / ETL 写作规范（复审常卡这几条）

1. **INSERT 必须写显式列清单**（col_list），禁止只靠列序对齐——加列会静默错位
2. StarRocks 不吃 Hive 式 `INSERT OVERWRITE tbl PARTITION (dt='...')`；月分区 PK 表用 INSERT INTO upsert
3. 改表结构前：rg 出所有写该表的 task，评估 DDL+ETL 同发
4. `bitmap_hash64_udf`、NOT NULL 主键：上游 NULL 会导致整批拒写，SQL 里要过滤
5. 小时任务 `${hour_*}` 占位符须在 task.yaml localParams 里声明

## 十、常见问题

**Q：test 有数就算能上 prod 吗？**  
A：不行。还要 playbook 对账、狂人复审、知秋放行，且 DDL 与 ETL 同批。

**Q：能不能本地改完直接改 prod 海豚？**  
A：不行。无审计、易清空参数，历史上出过事故。

**Q：session 在插件里看不见？**  
A：查 `project_id` 是否为 `dmp/dc-parent`，并 `git pull` 后本地有 `rel_dir`。

**Q：PI SUCCESS 但新列为全 NULL？**  
A：看 SQL 是否含 `enable_insert_strict=false`、解析路径是否错；SUCCESS ≠ 数据正确。
