## 一、背景：归因在算什么？

### 1.1 业务场景

推广链路典型路径：

```
用户点击广告 → 打开 H5 落地页（记录 IP、渠道、设备）→ 下载/打开 App → iOS 自然量注册
```

我们要回答的问题：**这次注册是不是来自某条推广渠道？** 如果是，应该把用户渠道从「自然量 organic」改成对应的推广渠道码。

### 1.2 匹配规则（产品版）

只有同时满足以下条件的注册，才会进入归因计算：

| 步骤 | 条件 | 通俗解释 |
|------|------|---------|
| ① 入围 | iOS + 自然量注册 + 客户端打「需归因」标记 | 客户端主动告诉系统「这个用户需要查渠道」 |
| ② IP 对齐 | 注册 IP = 落地页访问 IP | H5 和 App 必须在同一公网 IP 下（最难的一步） |
| ③ 时序 | 落地页访问在注册之前，且间隔 ≤ 24 小时 | 先点广告、后注册，不能超过一天 |
| ④ 渠道有效 | 落地页 channel ≠ organic | H5 必须上报真实推广渠道，不能填自然量 |
| ⑤ 打分过线 | 设备信息加分后总分 ≥ 40 | IP 命中 10 分，品牌/型号/系统等可加分 |

### 1.3 两个关键率（看板指标）

| 指标 | 公式 | 含义 |
|------|------|------|
| **有候选透率** | 有匹配记录数 ÷ 需归因注册数 | 多少比例的需归因用户，至少找到了一个可对齐的落地页 |
| **归因成功率** | 归因成功数 ÷ 有匹配记录数 | 进了归因计算后，最终判定为推广渠道的比例 |

> 注意：完全没有匹配到落地页的用户 **不会出现在结果表里**（不是「归因失败」，是「没有候选」）。

### 1.4 当前配置状态（全部 12 个 App）

所有相关 App 在归因配置表中均已开启计算（`is_run=1`），但均为**影子期**（`is_rewrite_channel=0`，只算结果、不改用户渠道）。通过分数门槛统一为 **40 分**。

### 4.4 漏斗拆解（以 7/5 为例，最细）

7/5 共 **2,275** 个需归因注册，逐步过滤如下：

```
2,275 需归因注册
  │
  ├─ 2,167 (95.3%) ──→ 注册 IP 在落地页日志里找不到同 IP ──→ 【无法归因，不出现在结果表】
  │
  └─ 108 有 IP 交集
       │
       ├─ 32 (1.4%) ──→ 落地页访问时间在注册之后 ──→ 时序不合法
       ├─ 21 (0.9%) ──→ IP 对上了但间隔超过 24 小时 ──→ 超出归因窗口
       │
       └─ 78 (3.4%) ──→ 通过 IP + 时序校验，进入归因计算
            │
            ├─ 54 (69%) ──→ 打分 ≥ 40，归因成功 ✅
            └─ 24 (31%) ──→ 打分 < 40，归因失败（低分）
```

**为什么「IP 交集 ~10%」但「有候选透率 ~3.4%」？**

因为 IP 交集只是第一步。108 个 IP 对上的用户里，约 30 个被时序规则（落地页在注册后 / 超 24h）淘汰，最终 78 个进入计算。

### 4.5 根因分析（三个层次）

#### 层次 1：IP 对不上（占 95%，主因）

| 可能原因 | 说明 | 是否 JHG-001 主因 |
|---------|------|----------------|
| H5 用 WiFi、App 用 4G | 运营商分配不同公网 IP | ✅ **最常见** |
| 运营商 NAT 复用 | 同一蜂窝出口 IP 被大量用户共享，时序对不上 | ✅ 常见 |
| 用户先注册后点落地页 | 时序反了 | 少量（1.4%） |
| 内网 IP（10.x / 192.168.x） | 注册侧拿到内网地址 | ❌ 仅占 3.3%，不是主因 |
| 埋点丢 IP | 注册或落地页没报 IP | ❌ IP 空值 = 0 |

#### 层次 2：时序淘汰（IP 对上了但仍出局，约 2.3%）

落地页访问必须在注册前 24 小时内。部分用户先注册了 App、后通过其他入口看到落地页，或落地页访问太早。

#### 层次 3：低分失败（进了计算但分数不够，约 1%）

打分规则（门槛 40 分）：

| 匹配项 | 分值 | 说明 |
|--------|------|------|
| IP 相同 | +10 | 基础分 |
| 设备品牌相同 | +10 | 如 Apple |
| 设备型号相同 | +20 | 如 iPhone / iPad |
| 系统名称相同 | +10 | 如 iOS |
| 系统版本相同 | +10 | 如 17.5 |
| 时间差 ≤ 1h | +20 | 落地页到注册 1 小时内 |
| 时间差 ≤ 6h | +10 | 1–6 小时 |
| 时间差 ≤ 24h | +5 | 6–24 小时 |

很多低分失败只有 IP 命中（10 分），缺少设备信息加分。

### 5.4 根因：落地页 channel 100% 为 organic

归因要求落地页上报**真实推广渠道**（如 `actuit88`、`bplodhkc`），`organic` 会被直接过滤。

**6/8 以来每日落地页点击 channel 分布：**

| 日期 | 点击总量 | channel=organic | 有效推广渠道 | 有效占比 |

| 6/15 | 13,446 | 13,446 | **0** | 0% |
| 6/23 | 8,972 | 8,972 | **0** | 0% |
| 6/26 | 1,259 | 1,259 | **0** | 0% |
| 7/1 | 5,227 | 5,227 | **0** | 0% |
| 7/4 | 25,022 | 25,022 | **0** | 0% |
| 7/5 | 14,935 | 14,935 | **0** | 0% |

**每一天、每一条落地页点击的 channel 都是 organic。** 不是没流量（每天几千到几万点击），是渠道字段填错了。

### 5.5 为什么「IP 无交集」

当所有落地页事件的 channel 都是 organic 时，归因 ETL 在第一步就把它们全部过滤掉。后续做 IP 匹配时，**有效落地页 IP 集合为空**，所以注册 IP 永远找不到匹配——表现为「IP 交集 = 0」。

这不是用户网络问题，是 **H5 埋点 channel 字段问题**。

## 九、业务修复手册（可直接转发研发）

### 9.1 注册侧：「需归因」标记

**事件**：`user_register`  
**位置**：`payload.attribution_flag`  
**值**：`1`（需要归因）/ `0` 或不传（不归因）

**触发条件（同时满足才打 1）**：

- 设备 = iOS
- 渠道 = organic（自然量）
- 业务判断该用户需要做推广渠道归因

**JSON 示例**：

```json
{
  "event": "user_register",
  "payload": {
    "attribution_flag": 1,
    "device": "ios",
    "channel": "organic",
    "device_brand": "Apple",
    "device_model": "iPhone",
    "system_name": "iOS",
    "system_version": "17.5.1"
  }
}
```

**对标**：JHG-001 当前标记率 7–14%，可作为初期目标。

### 9.2 H5 落地页：推广渠道

**事件**：`landing_page_click` / `landing_page_view`  
**位置**：`channel` 字段  
**值**：真实推广渠道码（从广告 URL 参数获取），**不能填 `organic`**

**错误示例**：

```json
{ "event": "landing_page_click", "channel": "organic" }
```

**正确示例**：

```json
{ "event": "landing_page_click", "channel": "actuit88" }
```

**涉及 App**：TJ-006、TJ-043、TJ-008（当前 100% organic）

### 9.3 注册侧：设备信息

| 字段 | 来源 | 示例 | 缺失影响 |
|------|------|------|---------|
| device_brand | SDK 原生 API | Apple | 少 10 分 |
| device_model | SDK 原生 API | iPhone 15 Pro | 少 20 分 |
| system_name | SDK 原生 API | iOS | 少 10 分 |
| system_version | SDK 原生 API | 17.5.1 | 少 10 分 |

缺失设备字段不会阻止入围，但会导致「IP 对上了却低分失败」。

**涉及 App**：DX 系列、YC 系列、TJ-008（缺失率 99–100%）

### 9.4 验收 SQL（业务修完后可用）

```sql
-- 1. 检查标记是否出现
SELECT app_id, dt,
  SUM(CASE WHEN attribution_flag=1 THEN 1 ELSE 0 END) AS flag1_cnt,
  COUNT(*) AS ios_organic_cnt
FROM dwd.dwd_user_register_d_v2
WHERE app_id = '你的AppID'
  AND dt >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY)
  AND channel='organic' AND LOWER(TRIM(device))='ios'
GROUP BY app_id, dt;

-- 期望：flag1_cnt > 0

-- 2. 检查落地页渠道（TJ 系列）
SELECT dt, channel, COUNT(*) AS cnt
FROM dwd.dwd_landing_page_click_d
WHERE app_id = '你的AppID' AND dt >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY)
GROUP BY dt, channel ORDER BY cnt DESC;

-- 期望：出现非 organic 的渠道码
```
